| 영역 | 1순위 권장 | 이유 한 줄 |
|------|-----------|-----------|
| **앱 프레임워크** | **Flutter** | 단일 코드로 iOS·Android, 알림/TTS 플러그인 성숙, UI 일관성 |
| **백엔드/클라우드** | **Firebase** | Auth·실시간 동기화·푸시(FCM)·서버리스를 한 묶음으로 가장 빠르게 |

| **사전 연동** | **딥링크 (네이버/구글)** | 공식 API 부재·약관 리스크 회피, 구현 단순 |

> 관계형(Postgres) 모델·RLS·오픈소스 선호로 Supabase로 확정했습니다. 설정은 `SUPABASE_설정가이드.md` 참고.

## 1. 앱 프레임워크: Flutter vs React Native vs KMP

| 비교 항목 | **Flutter** ✅ | React Native | Kotlin Multiplatform |
|-----------|---------------|--------------|----------------------|
| 언어 | Dart | JavaScript/TypeScript | Kotlin |
| iOS+Android 단일 코드 | ◎ | ◎ | △ (UI는 분리, 로직 공유) |
| UI 일관성 | ◎ 자체 렌더링, 픽셀 동일 | ○ 네이티브 컴포넌트 | 플랫폼별 네이티브 UI |
| 알림/TTS 플러그인 성숙도 | ◎ 1st-party급 다수 | ○ 다수지만 품질 편차 | △ 상대적으로 적음 |
| 성능 | ◎ (AOT 컴파일) | ○ (브리지/JSI) | ◎ |
| 학습 곡선 | 중 (Dart 새로 학습) | 낮음 (JS 친숙시) | 중~높음 |
| 개발 인력 풀 | 많음 | 매우 많음 | 적음 |
| 본 앱 적합도 | **최적** | 양호 | 과함 |

### 권장: **Flutter**
- 단어장 앱은 **커스텀 학습 UI(플래시/예문 입력/진행률 애니메이션)** 비중이 큼 → Flutter의 자체 렌더링이 유리
- 핵심 기능인 **로컬 알람·TTS** 모두 검증된 고품질 플러그인 존재
- 한 코드베이스로 iOS·Android 동시 출시 → MVP 속도

### React Native를 택할 경우
- 팀이 이미 **JS/TS·웹(React) 역량**이 강하면 합리적
- Expo 사용 시 알림·기본 기능 셋업이 빠르나, 일부 네이티브 알람 정밀 제어는 추가 작업 필요

> 결정 포인트: **팀의 기존 언어 역량**. JS 자산이 크면 RN, 그렇지 않으면 Flutter 권장.

## 2. 백엔드/클라우드: Firebase vs Supabase vs 커스텀

핵심 요구: **로그인 / 기기 간 실시간 동기화 / 오프라인 / 타인 공유(권한) / 서버발 푸시**

| 비교 항목 | **Firebase** ✅ | Supabase | 커스텀 (Node+DB 등) |
|-----------|----------------|----------|---------------------|
| DB 모델 | NoSQL (Firestore) | 관계형 (Postgres) | 자유 |
| 실시간 동기화 | ◎ 내장 | ◎ Realtime | 직접 구현 |
| 오프라인 캐시 | ◎ SDK 기본 제공 | △ (제한적) | 직접 구현 |
| 인증(Auth) | ◎ 구글/애플/이메일 | ◎ 다양 | 직접 구현 |
| 푸시(FCM) | ◎ 동일 생태계 | 별도 연동 | 별도 연동 |
| 서버리스 함수 | ◎ Cloud Functions | ◎ Edge Functions | 서버 운영 |
| 공유 권한 제어 | ○ 보안 규칙(Rules) | ◎ Postgres RLS(행 수준 보안) | ◎ 자유 |
| 복잡 쿼리/통계 | △ (NoSQL 한계) | ◎ SQL | ◎ |
| 무료 한도 | 넉넉 (Spark) | 넉넉 | 서버 비용 발생 |
| 운영 부담 | 낮음 | 낮음 | 높음 |
| 종속성(락인) | 높음 (구글) | 낮음 (오픈소스, 셀프호스트 가능) | 없음 |

### 권장: **Firebase (MVP)**
- **오프라인 동기화 + 푸시(FCM) + Auth가 하나의 생태계**로 묶여 알람·동기화 중심인 본 앱과 궁합 최고
- Flutter + Firebase는 1st-party 수준 통합(FlutterFire)
- 학습 통계가 단순한 MVP 단계에선 NoSQL로 충분

### Supabase가 더 나은 경우
- **타인 공유 권한**을 행 수준 보안(RLS)으로 정교하게 통제하고 싶을 때
- **학습 통계·랭킹·복잡 검색** 등 관계형 쿼리가 늘어날 때
- 벤더 종속을 피하고 싶을 때 (오픈소스·셀프호스트 가능)

> 전략: **MVP는 Firebase로 빠르게**, 공유·통계 기능이 본격화되어 관계형 요구가 커지면 Supabase 검토. (데이터 접근 계층을 추상화해두면 이전 비용 절감)

## 3. 알람 / 푸시 (★본 앱 최우선 기능)

알람은 **두 종류**로 나눠 설계한다.

### 3.1 로컬 알람 (기기 자체 예약 알림)
- **용도**: "매일 9시", "3시간마다" 같은 **사용자 지정 정시 반복 알림**
- **권장**: `flutter_local_notifications`
  - 정확한 시각(exact alarm)·반복·타임존 지원
  - 오프라인·서버 불필요
- **주의 (OS 제약 — 기획문서 Open Issue #6)**:
  - **Android**: 14 이상 정확한 알람은 `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` 권한, Doze 모드 대응 필요
  - **iOS**: 백그라운드 임의 시각 실행 제약 → 로컬 알림 예약(최대 64개 pending) 방식으로 우회

### 3.2 서버 푸시 (원격 발송)
- **용도**: **SRS 복습 리마인드**("복습할 단어 12개"), 공유 단어장 업데이트 알림
- **권장**: **FCM (Firebase Cloud Messaging)** — 무료, Cloud Functions로 스케줄 발송
  - 예: Cloud Scheduler + Functions로 사용자별 복습 도래 시점에 푸시

### 설계 권장
| 알림 성격 | 방식 |
|-----------|------|
| 사용자가 정한 고정 시간 학습 알림 | 로컬 알람 (flutter_local_notifications) |
| 복습 도래(SRS)·공유 변경 등 동적 알림 | 서버 푸시 (FCM + Functions) |

## 4. 발음 (TTS) — 기획: TTS 우선 + 사전 연동

| 옵션 | 음질 | 비용 | 오프라인 | 권장 단계 |
|------|------|------|----------|-----------|
| **기기 내장 TTS** (`flutter_tts`) | 보통~양호 | 무료 | ◎ | **MVP** |
| **Google Cloud TTS / Azure TTS** | 매우 자연스러움(신경망) | 사용량 과금 | ✕ | 2~3단계 옵션 |
| 사전 제공 원어민 음원 | 원어민 | 직접 재생 시 약관 확인 필요 | ✕ | 연동(딥링크) 형태 권장 |

### 권장
- **MVP: `flutter_tts`** — 단어·예문 즉시 재생, 미국식/영국식(locale) 선택, 비용 0
- **고품질 옵션(유료/프리미엄)**: Google Cloud TTS를 Cloud Functions 경유로 호출 → 음원 캐싱
- 캐싱으로 반복 재생 시 비용·지연 절감

## 5. 사전 연동 (네이버/구글) — Open Issue #2

| 방식 | 설명 | 리스크 | 권장 |
|------|------|--------|------|
| **딥링크/웹뷰** ✅ | 해당 단어의 네이버/구글 사전 페이지로 이동 | 낮음 (단순 링크) | **권장** |
| 공식 오픈 API | 사전 검색 API 제공 여부·약관 확인 필요 | 정책 변경·종료 가능 | 가능 시 보조 |
| 스크래핑 | 페이지 직접 파싱 | **약관 위반·차단 위험 높음** | **비권장** |

### 권장
- 발음/예문 "더 보기"는 **딥링크**로 네이버 사전·구글 번역에 위임 (구현 단순, 법적 리스크 최소)
- 음원·콘텐츠를 앱 내부에 직접 재생/저장하는 방식은 **저작권·약관 검토 필수**
- 기본 발음은 자체 TTS로 제공해 외부 의존도를 낮춤

## 6. 데이터 모델 적합성 메모

- **Firestore(NoSQL)**: 단어/단어장/예문처럼 **문서 단위로 묶여 동기화**되는 구조에 잘 맞음. 단, "정답률 상위 N", "지난 7일 학습량" 등 집계는 별도 집계 문서/필드를 유지해야 함.
- **Supabase(Postgres)**: 위 집계·공유 권한(RLS)·검색을 SQL로 깔끔히 처리. 오프라인 동기화는 직접 보강 필요.
- 어느 쪽이든 **클라이언트의 데이터 접근부를 Repository 패턴으로 추상화**해 백엔드 교체 비용을 낮출 것.

## 7. 최종 권장 조합 & 단계 전략

### 권장 스택 (MVP)
```
앱        : Flutter (Dart)
백엔드    : Firebase
            ├ Auth        (구글/애플/이메일 로그인)
            ├ Firestore   (단어장·단어·예문, 오프라인 동기화)
            ├ FCM         (서버 푸시)
            └ Functions   (SRS 복습 푸시 스케줄)
로컬 알람 : flutter_local_notifications
발음 TTS  : flutter_tts (기기 내장)
사전 연동 : 네이버/구글 딥링크
상태관리  : Riverpod 또는 Bloc (Flutter 표준 중 택1)
```

### 단계별
| 단계 | 백엔드 | TTS | 비고 |
|------|--------|-----|------|
| **MVP** | Firebase | flutter_tts | 빠른 출시·검증 |
| **확장** | Firebase 유지 (필요 시 Supabase 검토) | + Cloud TTS 옵션 | 공유·통계 고도화 |
| **고도화** | 관계형 요구 크면 Supabase 이전 검토 | 프리미엄 음질 | 데이터 계층 추상화 전제 |
